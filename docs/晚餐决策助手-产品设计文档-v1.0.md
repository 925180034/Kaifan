## 1. 背景与问题定义

### 1.1 要解决的问题

每天下班前,"今晚吃什么"是一个高频、低价值但消耗决策精力的问题。它不只是"吃哪道菜",而是同时包含四个选择:

- **吃什么**:口味、营养、份量、近期是否重复;
- **怎么吃**:自己做、点外卖、出去吃;
- **买什么**:如果自己做,需要哪些食材、是否可以顺手采购;
- **为什么是这个**:用户需要一个足够可信的理由,才会少纠结、少换一批。

现有工具通常只解决局部:菜谱 App 假设用户已经决定做饭,外卖 App 假设用户已经决定点外卖,点评 App 假设用户已经决定出门吃。这个产品要补的是"决策层":先帮用户判断今晚最适合怎么吃,再把后续动作接起来。

### 1.2 产品定位

**一句话定位**:一个基于个人画像和当日情境的晚餐决策助手,每天用 30-60 秒给用户一个可执行的"今晚方案包",覆盖自己做、点外卖、出去吃和买菜跳转。

产品的本质不是"菜谱生成工具",而是"晚餐决策工具"。菜谱、购物清单、外卖搜索词、点评搜索词都是决策后的履约环节。

### 1.3 推荐产品形态

**MVP 推荐形态:先做 H5/PWA,架构上预留小程序。**

原因:

- H5 迭代最快,无审核,适合先验证推荐质量和真实使用频率;
- 可以通过链接发给朋友试用,适合种子用户阶段;
- 可以做 PWA 加主屏,缓解入口问题;
- 后续小程序可以复用同一套后端和推荐服务,只替换前端壳。

**成熟期推荐形态:小程序 + H5 共用后端。**

- 小程序负责日常入口、微信生态访问、提醒触达;
- H5 负责快速分享、公开访问、桌面端调试和管理页;
- 后端保持独立,画像、推荐、菜谱缓存和埋点都不绑定某一个端。

**不建议第一版同时做 H5 和小程序。** 双端会把精力消耗在适配、审核、发布和平台差异上,反而拖慢最关键的验证:用户是否真的愿意每天用它做晚餐决定。

### 1.4 目标用户

- **核心用户**:一二线城市上班族/学生,1-3 人吃饭规模,会做基础家常菜,但不想每天想菜单,也高频使用外卖;
- **次级用户**:有减脂、增肌、控糖、控预算等明确目标的人;
- **早期种子用户**:作者本人及朋友,以真实晚餐决策为验证场景。

### 1.5 非目标(Non-Goals)

MVP 阶段明确不做:

- 不做自动下单、自动支付;
- 不逆向、不爬取美团/大众点评/小象超市的私有接口;
- 不在产品内展示三方平台的真实店铺、商品、价格、库存;
- 不做社区、菜谱 UGC、餐厅点评;
- 不做完整健康管理或医疗饮食建议;
- 不一开始做多端同步、小程序审核、商业化支付。

## 2. 产品目标与成功指标

| 目标 | 指标 | MVP 达标线 |
| --- | --- | --- |
| 验证决策价值 | 种子用户连续使用天数 | 连续 2 周每天使用 |
| 降低纠结 | 从打开到采纳方案的时长 | 中位数 <= 60 秒 |
| 推荐质量 | 单次决策"换一批"次数 | 平均 <= 1 次 |
| 采纳率 | 推荐方案被采纳比例 | >= 70% |
| 画像积累 | 每日有效反馈事件 | >= 3 条/人/天 |
| 履约顺滑 | 选择后进入菜谱/复制清单/跳转搜索比例 | >= 70% |

核心判断标准不是"生成内容看起来丰富",而是用户是否真的少想了、少纠结了、并完成了晚餐决策。

## 3. 核心产品策略

### 3.1 从"三选一"升级为"今晚方案包"

首页仍然展示自己做、点外卖、出去吃三个方向,但每个方向都不是单薄的建议,而是一个可执行方案包:

- **自己做方案包**:菜品组合、预计耗时、预计成本、营养概要、所需食材、购物清单、小象搜索入口;
- **点外卖方案包**:推荐品类、搜索关键词、预算建议、适合原因、美团跳转入口;
- **出去吃方案包**:推荐餐饮方向、适合商圈/距离偏好、搜索关键词、大众点评跳转入口。

用户看到的不是"你可以吃面",而是"今晚建议吃一碗热汤面:下雨、到家晚、预算 30 元内、你最近没吃过面食。点击可跳美团搜'热汤面 少油 高评分'。"

### 3.2 增加"帮我直接定"主按钮

三张卡片保留选择权,但首页应有一个更符合产品定位的主按钮:

> **别问了,就这个**

点击后系统直接采纳排名第一的方案,进入对应履约页。这个按钮服务于最累、最不想选择的用户,也是产品"减少决策"的精神锚点。

### 3.3 推荐解释要短,但必须具体

每张卡片的推荐理由控制在 1-2 句话,避免 AI 味过重。理由需要落到具体因素:

- 天气:"今晚有雨,出门成本高";
- 情绪:"你选择了偷懒模式,优先 20 分钟内";
- 画像:"你偏好川湘和豆腐,但最近 7 天没吃豆制品";
- 预算:"预计每人 25 元,低于你的常规预算";
- 营养:"蛋白质来自鸡蛋和虾仁,比单吃粉面更均衡"。

### 3.4 MVP 只做推荐闭环,不做平台数据闭环

MVP 要解决的是"给出靠谱选择",不是"替代美团/点评/小象"。三方平台只做搜索入口:

- 推荐品类和关键词;
- 复制关键词;
- 尝试深链跳转;
- 深链失败则降级到浏览器搜索或复制。

## 4. 用户画像系统设计

画像是推荐质量的核心资产。设计原则是:

- 冷启动极轻,30 秒内完成;
- 深度画像可选,不要一上来审问用户;
- 行为画像自动积累,用真实选择修正自我描述;
- 情境画像每日变化,决定今晚到底适合什么。

### 4.1 第一层:冷启动画像(MVP 必填)

首次进入只问 5 个问题,全部点选:

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| 用餐人数 | 单选:1 / 2 / 3-4 / 5+ | 决定份量、菜数、预算 |
| 忌口与过敏 | 多选:香菜、内脏、海鲜、花生等 | 硬约束,不可违反 |
| 辣度 | 单选:不吃辣 / 微辣 / 中辣 / 重辣 | 硬偏好 |
| 每餐预算 | 单选:15 以下 / 15-30 / 30-60 / 60+ 每人 | 推荐排序和成本提示 |
| 做饭意愿 | 单选:不想做 / 简单做 / 正常做 / 想露一手 | 决定自己做方案复杂度 |

可选第 6 问:

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| 口味方向 | 多选:家常、川湘、粤式、江浙、西式、日韩、面食 | 冷启动排序 |

### 4.2 第二层:深度画像(设置页渐进补充)

| 分类 | 字段 | 示例 |
| --- | --- | --- |
| 口味偏好 | 喜爱菜系、喜欢味型、讨厌口感 | 酸辣、番茄味、不喜欢软烂茄子 |
| 食材偏好 | 喜爱食材、拉黑食材、常备食材 | 鸡胸肉、虾、豆腐;不吃羊肉 |
| 主食偏好 | 米饭、面、粉、低碳水 | 晚上少吃米饭 |
| 营养目标 | 普通均衡、减脂、增肌、控糖 | 减脂优先高蛋白 |
| 厨具条件 | 电饭煲、空气炸锅、烤箱、蒸锅 | 只有电饭煲 |
| 烹饪能力 | 小白、家常、熟练、爱折腾 | 会基础炒菜 |
| 时间限制 | 15 分钟、30 分钟、45 分钟、不限 | 工作日晚餐 30 分钟内 |
| 消费习惯 | 外卖预算、到店预算、是否接受排队 | 到店不想排队 |
| 平台偏好 | 常用美团/点评/小象/盒马等 | 买菜优先小象 |

### 4.3 第三层:情境画像(每日轻量输入)

情境画像决定"今天"而不是"长期"。建议首页用一个小控件收集:

| 字段 | 选项 | 影响 |
| --- | --- | --- |
| 今日状态 | 偷懒 / 正常 / 想吃好点 | 决定复杂度和预算弹性 |
| 饥饿程度 | 随便吃 / 正常 / 很饿 | 决定份量和主食占比 |
| 时间压力 | 赶时间 / 正常 / 不急 | 决定是否推荐出门或复杂菜 |
| 省钱开关 | 开 / 关 | 提升自己做、拼饭、简餐权重 |
| 健身后 | 是 / 否 | 提升蛋白质和低油方案权重 |
| 天气 | 自动获取 | 雨天降低出去吃,冷天提高热汤炖菜 |

MVP 可以先做"今日状态"三档,天气自动获取;其余字段后续加入。

### 4.4 第四层:行为画像(自动积累)

系统自动记录:

- 每天展示过哪些方案;
- 用户采纳了哪一张卡;
- 换掉了哪些菜或品类;
- 点击了哪些履约动作;
- 做完后的简单反馈;
- 近 14 天吃过什么;
- 自己做、外卖、出去吃的长期比例;
- 实际选择是否偏离自我画像。

行为画像要能修正用户自述。例如用户说自己清淡,但连续采纳红烧、麻辣、炸物,系统应该逐步降低"清淡"权重。

### 4.5 反馈标签设计

饭后反馈不要做复杂评分,只做 3 秒能答的标签:

- 好吃,下次还吃;
- 太贵;
- 太麻烦;
- 没吃饱;
- 太油/太咸;
- 不合口味;
- 再也不吃。

这些标签比 1-5 星更适合训练推荐。

## 5. 决策引擎设计

### 5.1 决策引擎目标

决策引擎不只是调用 LLM 生成内容,而是把用户画像、情境、规则和 LLM 结合起来,输出可执行、可解释、可校验的方案。

输入:

- 用户画像;
- 当日情境;
- 天气;
- 近 14 天历史;
- 预算和时间限制;
- 平台履约能力。

输出:

- 三个方向的候选方案;
- 排名第一的推荐方案;
- 推荐理由;
- 履约动作;
- 结构化数据快照。

### 5.2 约束分层

| 层级 | 内容 | 处理方式 |
| --- | --- | --- |
| 硬约束 | 过敏、忌口、厨具不可用、预算上限、时间上限 | 不允许违反,违反则丢弃或重试 |
| 强偏好 | 辣度、做饭意愿、营养目标 | 尽量满足,冲突时给解释 |
| 软偏好 | 菜系、喜欢食材、主食偏好 | 用于排序加权 |
| 情境权重 | 天气、疲劳、时间压力、省钱 | 影响三种吃法权重 |
| 近期去重 | 近 14 天已吃 | 降权或过滤 |

### 5.3 推荐流程

1. 读取用户画像和今日情境;
2. 生成三类方向的候选池:自己做、点外卖、出去吃;
3. 应用硬约束过滤;
4. 应用预算、时间、天气、近期去重等规则打分;
5. 调用 LLM 生成结构化方案;
6. 后端做 JSON Schema 校验;
7. 做合理性校验:食材用量、耗时、成本、营养描述;
8. 生成最终卡片和履约动作;
9. 保存决策快照,用于反馈和复盘。

### 5.4 排序策略示例

权重初始可规则化,后续再根据行为反馈调整:

| 因素 | 示例影响 |
| --- | --- |
| 雨天 | 出去吃 -20 分,外卖 +10 分,自己做 +5 分 |
| 偷懒模式 | 复杂菜 -30 分,20 分钟内方案 +20 分 |
| 健身后 | 高蛋白方案 +20 分,纯碳水方案 -15 分 |
| 预算紧 | 自己做 +20 分,到店吃 -20 分 |
| 近 7 天吃过 | 同类菜品 -20 分 |
| 用户多次换掉 | 对应菜品或品类 -30 分 |

### 5.5 LLM 输出要求

LLM 必须输出结构化 JSON,不要让前端解析自然语言。核心结构:

```json
{
  "date": "2026-07-06",
  "topRecommendation": "cook",
  "cards": [
    {
      "type": "cook",
      "title": "番茄虾仁豆腐饭 + 拍黄瓜",
      "reason": "你今天选择偷懒模式,这套 25 分钟能完成,也符合你喜欢虾和豆腐的偏好。",
      "estimatedMinutes": 25,
      "estimatedCostPerPerson": 28,
      "nutritionSummary": {
        "calories": "约 620 kcal/人",
        "protein": "约 34 g/人",
        "note": "蛋白质较充足,油脂适中"
      },
      "actions": ["view_recipe", "copy_shopping_list", "open_grocery_search"]
    }
  ]
}
```

### 5.6 推荐失败兜底

| 失败场景 | 兜底策略 |
| --- | --- |
| LLM 超时 | 展示本地规则推荐或最近高评分菜谱 |
| JSON 校验失败 | 自动重试 1 次,仍失败则降级模板 |
| 菜谱违反忌口 | 丢弃并重试 |
| 成本明显不合理 | 用价格区间展示,不显示精确值 |
| 深链失效 | 复制关键词 + 打开平台官网搜索页 |
| 天气接口失败 | 不使用天气权重,推荐理由不提天气 |
| 没有历史数据 | 使用冷启动画像和通用热门家常方案 |

## 6. 核心功能设计

### 6.1 今日决策页(MVP 核心)

页面结构:

- 日期、天气、当前位置粒度提示;
- 今日状态三档:偷懒 / 正常 / 想吃好点;
- 主推荐区:"别问了,就这个";
- 三张方案卡:自己做 / 点外卖 / 出去吃;
- 每张卡支持"选这个"、"换一批"、"不想吃这个"。

### 6.2 卡片 A:自己做

内容:

- 菜品组合,优先一人食或 2 人家常;
- 预计耗时;
- 预计成本;
- 食材清单;
- 营养概要;
- 难度等级;
- 推荐理由;
- 菜谱详情入口;
- 购物清单复制和小象搜索入口。

复杂度由今日状态决定:

| 状态 | 方案 |
| --- | --- |
| 偷懒 | 一锅出、盖饭、面、空气炸锅、20 分钟内 |
| 正常 | 1-2 菜 + 主食,30-45 分钟 |
| 想吃好点 | 可包含一道硬菜,允许 45 分钟以上 |

### 6.3 卡片 B:点外卖

内容:

- 推荐 2-3 个品类方向;
- 预算建议;
- 搜索关键词;
- 推荐理由;
- 美团搜索跳转;
- 复制关键词。

注意:

- MVP 不展示真实商家;
- 不承诺价格、配送时间、库存;
- 只负责给搜索策略,由平台完成最终选择。

### 6.4 卡片 C:出去吃

内容:

- 推荐餐饮方向;
- 适合理由;
- 人均预算;
- 搜索关键词;
- 大众点评搜索跳转;
- 复制关键词。

出去吃推荐应考虑:

- 天气;
- 是否加班;
- 是否适合一人食;
- 是否需要排队;
- 预算;
- 距离偏好。

### 6.5 菜谱详情

结构:

- 菜名和一句话描述;
- 耗时、难度、成本、营养概要;
- 食材清单,支持勾选;
- 步骤,每步有时间和关键火候;
- 常见翻车点;
- 替代食材;
- 做完反馈。

菜谱生成后缓存,同一道菜不重复生成。

### 6.6 购物清单

MVP 能力:

- 从菜谱自动提取食材;
- 按生鲜、肉蛋奶、主食、调料分组;
- 支持勾选;
- 支持一键复制;
- 支持按食材生成小象搜索关键词;
- 跳转失败时保留复制文案。

### 6.7 周菜单(P2)

周菜单不是 MVP 必需。P2 再做:

- 周日晚生成下周 7 天草案;
- 用户逐日替换;
- 自动合并采购清单;
- 复用当日决策页展示当天自己做方案。

### 6.8 冰箱模式(P2)

先做手动记录,后做拍照识别:

- 手动添加常备/临期食材;
- 推荐优先消耗临期食材;
- 拍照识别只作为辅助,结果必须可编辑。

### 6.9 吃饭记账(P2)

自动记录预估花费,用户可改为实际花费。周报展示:

- 本周伙食总支出;
- 自己做、外卖、出去吃比例;
- 每种方式均价;
- 比预算高/低多少。

## 7. 第三方平台对接策略

### 7.1 核心原则

MVP 阶段不做平台数据抓取,只做"推荐搜索策略 + 跳转"。

| 平台 | MVP 对接 | 展示内容 |
| --- | --- | --- |
| 美团外卖 | 深链或网页搜索跳转 | 品类、搜索词、预算建议 |
| 大众点评 | 深链或网页搜索跳转 | 餐饮方向、搜索词、人均建议 |
| 小象超市 | 搜索跳转 + 购物清单复制 | 食材关键词、清单文本 |

### 7.2 为什么不做自动下单

自动下单涉及登录态、支付、风控、验证码、平台规则和资金安全。即使技术上能模拟,也不适合作为早期功能。

远期可以探索"半自动购物车":

- 系统生成清单;
- 用户手动进入平台;
- 用户自行加购、确认、支付;
- 产品不接触支付密码和扣款流程。

### 7.3 搜索词生成规范

外卖搜索词示例:

- `热汤面 少油 高评分`
- `鸡胸肉 轻食 高蛋白`
- `砂锅粥 一人食`
- `麻辣烫 少油 可选菜`

点评搜索词示例:

- `附近 粤菜 双人 人均100以内`
- `附近 日料 一人食`
- `附近 热汤 火锅 不排队`

小象搜索词示例:

- `番茄`
- `虾仁`
- `嫩豆腐`
- `黄瓜`

## 8. 关键用户流程

### 8.1 首次使用

打开 H5 -> 欢迎页 -> 5 问冷启动画像 -> 生成今日方案 -> 用户采纳或换一批 -> 进入履约。

原则:

- 不做注册墙;
- 本地生成匿名用户 ID;
- 首次必须直接给出价值。

### 8.2 每日决策

打开首页 -> 选择今日状态 -> 查看主推荐和三张卡 -> 点击"别问了,就这个"或手动选择 -> 进入菜谱/平台跳转 -> 饭后简单反馈。

### 8.3 自己做履约

选择自己做 -> 菜谱详情 -> 勾选食材 -> 复制清单或跳小象 -> 做完反馈。

### 8.4 外卖履约

选择外卖 -> 查看推荐品类和搜索词 -> 跳美团搜索 -> 用户在美团内自行选择店铺下单 -> 回来可反馈。

### 8.5 出去吃履约

选择出去吃 -> 查看推荐餐饮方向和搜索词 -> 跳大众点评搜索 -> 用户在点评内选择餐厅 -> 回来可反馈。

## 9. 技术架构

### 9.1 总体架构

```text
[H5/PWA 前端]
      |
      | HTTPS
      v
[后端 API]
  |-- 用户画像服务
  |-- 情境与天气服务
  |-- 决策引擎
  |-- LLM 适配层
  |-- 结构化校验
  |-- 菜谱缓存
  |-- 深链/搜索词服务
  |-- 埋点与反馈服务
      |
      v
[SQLite(MVP) -> MySQL(多用户后)]
```

### 9.2 技术选型建议

MVP:

- 前端:H5/PWA,React 或 Vue 均可;
- 后端:FastAPI 或 Spring Boot,优先选作者更熟的栈;
- 数据库:SQLite;
- LLM:国内可直连模型 API,保留多供应商适配层;
- 天气:免费天气 API;
- 部署:复用现有阿里云 ECS。

P2/P3:

- 小程序端接入同一套 API;
- SQLite 迁移 MySQL;
- 加登录体系和多用户数据隔离;
- 提醒能力接微信服务号、企业微信机器人或小程序订阅消息。

### 9.3 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| user | id, anonymous_id, created_at | MVP 匿名用户 |
| profile_static | user_id, 人数, 忌口, 辣度, 预算, 做饭意愿, 口味 | 冷启动画像 |
| profile_deep | user_id, 营养目标, 喜爱食材, 拉黑食材, 厨具, 时间限制 | 深度画像 |
| context_daily | user_id, date, 今日状态, 饥饿程度, 省钱开关, 天气 | 每日情境 |
| decision_log | user_id, date, cards_json, top_recommendation, selected_type, refresh_count | 决策快照 |
| recipe_cache | dish_id, title, ingredients_json, steps_json, nutrition_json | 菜谱缓存 |
| feedback_log | user_id, decision_id, tags, note, created_at | 饭后反馈 |
| link_template | platform, type, template_url, enabled | 深链配置 |
| weekly_plan | user_id, week, menu_json, shopping_list_json | P2 周菜单 |

## 11. 隐私、合规与安全

### 11.1 数据最小化

MVP 只收集完成推荐所需的信息:

- 忌口、过敏、口味;
- 预算、做饭意愿;
- 决策和反馈记录;
- 粗粒度位置或手动城市,不要默认精确定位。

### 11.2 健康与营养边界

营养信息只做估算和生活建议,不作为医疗建议。控糖、疾病、过敏相关内容必须保守:

- 过敏作为硬约束;
- 控糖只给低糖/低 GI 倾向建议;
- 不承诺治疗效果;
- 必要时提示咨询专业人士。

### 11.3 AIGC 合规

如果未来面向公众开放,需关注生成式 AI 服务相关合规要求:

- 用户协议和隐私政策;
- 投诉与删除入口;
- 生成内容准确性提示;
- 对违法内容和不当输入的处理;
- 使用已合规的大模型服务商。

MVP 个人和朋友试用阶段,仍建议按最小化收集和可删除原则设计,避免后续返工。

## 12. 版本规划

### MVP(P1,1-2 周业余开发)

目标:验证"每天打开后 60 秒内完成晚餐决策"。

范围:

- H5/PWA;
- 冷启动画像 5 问;
- 今日状态三档;
- 今日三张方案卡;
- "别问了,就这个"主按钮;
- 自己做菜谱详情;
- 购物清单复制;
- 美团/点评/小象搜索词和跳转;
- 换一批;
- 简单反馈;
- 行为日志;
- 天气联动;
- SQLite 和匿名用户。

不做:

- 登录;
- 小程序;
- 周菜单;
- 自动下单;
- 真实店铺/商品数据;
- 冰箱拍照识别。

### P2(MVP 验证后 1 个月)

- 深度画像;
- 行为画像正式参与推荐;
- 周菜单和聚合采购清单;
- 冰箱模式手动版;
- 吃饭记账周报;
- 微信服务号或企微提醒;
- 历史记录。

### P3(产品成型后)

- 小程序端;
- 微信登录;
- 多用户与数据同步;
- 家庭共享;
- 更完整的营养目标;
- 小程序订阅消息。

### P4+(远期探索)

- 半自动购物车;
- 合规真实店铺/商品数据源;
- 会员或订阅;
- 与健康数据联动;
- 多人偏好协调。

## 13. 风险与应对

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 推荐质量差 | 高 | 种子用户每日真实使用,用换一批和反馈快速调 prompt/规则 |
| H5 触达弱 | 高 | PWA 加主屏,用户自设提醒,P2 接微信提醒 |
| 范围膨胀 | 高 | MVP 严格只做今日决策闭环 |
| LLM 输出不稳定 | 中 | JSON Schema 校验、重试、规则兜底 |
| 菜谱不合理 | 中 | 用量/耗时/成本校验,高频菜谱缓存人工修正 |
| 深链失效 | 中 | 链接配置化,降级复制关键词 |
| 营养建议被误解 | 中 | 明确估算属性,不做医疗承诺 |
| 用户隐私风险 | 中 | 匿名、本地优先、最小收集、可删除 |
| 小程序审核不确定 | 中 | 先 H5 验证,小程序作为 P3 |

## 14. Open Questions

## 15. MVP 验收标准

MVP 完成后,连续 14 天记录:

- 每天是否打开;
- 从打开到采纳用时;
- 采纳了哪种方式;
- 换一批次数;
- 是否完成履约动作;
- 饭后反馈;
- 有没有第二天愿意继续用。

如果 14 天后仍愿意每天打开,且平均 60 秒内完成决策,说明这个方向值得继续做小程序和 P2 功能。
